# NMM Agent Conventions

Conventions for coding agents working in an NMM application repo scaffolded from
`nmm-base`. This complements the root `CLAUDE.md` (general project rules) with the
NMM-specific patterns every API and SPA in the system follows.

## Canonical references

- **`nmm_functional_spec_v17.md`** — the canonical system specification. The
  source of truth for entities, endpoints, state machines, the event catalogue
  (section 8), delivery/idempotency semantics (section 9), notifications
  (section 19), the permission matrix (section 31), and record-page conventions
  (section 41). When behaviour is ambiguous, the spec decides.
- **`nmm_build_plan_v15.md`** — the construction plan. Defines the repository
  topology, the shared packages, the work order, and which artefacts block which
  steps.

These two documents live in the `nmm` repo's `docs/`. An application repo carries
forward the patterns below; it does not duplicate the spec.

## System shape

NMM is several independent FastAPI services (Delivery API, SU MM API, Advertiser
API), each its own repo with its own Postgres, Redis/RQ, and Heroku app, plus
their Vite SPAs. Services never call each other synchronously to write. All
cross-service state change flows through the RabbitMQ message bus via the outbox
pattern. See `docs/cross-api-events.md` and `docs/architecture-patterns.md`.

## Core patterns

- **OpenAPI is an exported artefact, never authored.** The FastAPI route
  signatures and Pydantic schemas are the source of truth. `<api>.openapi.json`
  at the repo root is generated by `python -m scripts.export_openapi` and gated
  in CI. SPAs and the Publisher Widget generate their TypeScript clients from it.
  See `docs/openapi-export.md`.
- **Outbox transactionality.** An endpoint that changes cross-API state writes
  its local row and an outbox row in one transaction, commits, and returns. The
  outbox relay publishes the event. Never write to another service's database.
- **Event consumers encode business logic.** A consumer handler runs the
  projection update plus any derived computation and downstream outbox writes in
  a single transaction — not just a row copy.
- **Projection tables carry a tenant column** populated by the consumer worker
  from the event envelope, never by an HTTP request handler.
- **Multi-tenancy is enforced by a listener** (forward reference:
  **`nmm-tenancy`**). The JWT validation dependency sets a tenant contextvar on
  every request before any query runs; the listener intercepts every Select,
  Update, and Delete against tenant-scoped tables. `native_staff` users bypass
  via the contextvar value `{"type": "native_bypass"}`. Each repo ships a
  `scripts/fixtures/cross_tenant_isolation.py` run by the harness.
- **JWT validation is a shared dependency factory** (forward reference:
  **`nmm-auth`**), parameterised by audience and role taxonomy. It validates the
  token and derives the tenant contextvar from a JWT custom claim. It does not
  evaluate permissions — the role-permission matrix lives on each API's own
  admin tables per spec section 31.

## Runtime vs scaffold-time packages

`nmm-base` is a scaffold template, not a runtime dependency. A scaffolded repo
evolves independently. The shared runtime packages — `nmm-events`,
`nmm-event-contracts`, `nmm-tenancy`, `nmm-auth` — are added by each application
repo after scaffolding (build-plan step 3+), pinned by exact version. They are
not listed in `nmm-base`'s `pyproject.toml`.

## Harness

`python manage.py harness` runs the repo's fixtures against the live dev stack.
See `docs/harness-conventions.md` for the pattern carried forward from `nmm`.

## Frontend

Each SPA is a Vite app under `frontends/` generating its client from the repo's
OpenAPI document, mocked with Prism during development. The default component
library is `nmm-ui` (`docs/nmm-ui.md`); `native-ui` is the per-project
alternative (`docs/native-ui.md`). See `docs/frontends.md`.
